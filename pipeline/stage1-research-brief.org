* 1. Research Question Brief

** Refined research question
#+begin_quote
For irregular graph workloads (traversal, analytics and mining), how do Processing-in-Memory (PIM) architectures and discrete Domain-Specific Accelerators (DSAs) trade off throughput, energy efficiency, and effective memory bandwidth, and which workload and system assumptions decide when each is better?
#+end_quote

(Fixes from =selected-topic.org=: "comparete" → "compare"; "energy efficient" → "energy efficiency". It also makes the "it depends on X" framing an explicit question, since that is where the corpus' strongest contribution lies.)

** Sub-questions
- *SQ1 (mechanism)*: Which bottleneck does each camp attack (data movement vs. pipeline/locality mismatch), and how has each lineage evolved since 2015?
- *SQ2 (evidence)*: What do reported results support once baselines, datasets, and evaluation substrate (simulation vs. silicon/FPGA) are normalized? Where can they *not* be compared?
- *SQ3 (assumptions)*: Which assumptions (static vs. dynamic graph, access granularity, partitionability/skew, graph size vs. memory capacity, single vs. concurrent queries) decide which camp wins?
- *SQ4 (critical systems)*: How do the two camps differ in security, dependability, and predictability, and what is still unaddressed?

** Scope
- *In*: ASIC/PIM/near-data designs (and FPGA+HBM only as a reference point for DSAs) for BFS/SSSP/PageRank/CC, graph mining/pattern matching, streaming/evolving graphs; real-PIM (UPMEM) characterization studies.
- *Out*: GNN training/inference accelerators; GPU-only and pure-software graph systems (used only as baselines); storage-level (near-SSD) graph processing.
- *Decision needed (scope consistency)*: ReGraph (FPGA) is in the matrix, yet FPGAs are otherwise excluded. Recommended: keep ReGraph, and say in one sentence in the paper that FPGA+HBM serves as a reference point for DSAs, with ASIC DSAs as the primary comparison.

* 2. Methodology Blueprint

- *Paradigm / method*: Qualitative comparative survey (structured narrative review) with a fixed extraction scheme. It is not a systematic review or meta-analysis. Reported numbers are *not* pooled, because baselines differ.
- *Unit of analysis*: one architecture paper.
- *Extraction sheet (one row per paper; feeds Tables 1–3)*:
  | Field | Values |
  |-------+--------|
  | Camp | PIM-digital / PIM-analog(ReRAM) / PIM-real(UPMEM) / DSA-ASIC / DSA-FPGA / Hybrid |
  | Workloads | BFS, SSSP, PR, CC, TC, GPM, streaming |
  | Evaluation substrate | cycle-level sim / analytical model / FPGA prototype / real silicon |
  | Baseline | 1T CPU / MT CPU / GPU / prior accelerator / non-PIM SOTA |
  | Datasets & max graph size | e.g., LJ, Twitter, Friendster; |V|, |E| |
  | Reported speedup / energy (as stated, *with baseline*) | verbatim + page ref |
  | Bandwidth assumption | internal BW (TSV/bank), external BW |
  | Key assumptions | static/dynamic, partitioning, skew handling, fits-in-memory, single/concurrent query |
  | Critical-systems engagement | security / dependability / predictability: none / mentioned / evaluated |
- *Comparison rule*: a speedup or energy number may appear next to another only if both share baseline class *and* substrate. Otherwise the table cell gets a footnote marker and the text says "not comparable". This turns the corpus' main weakness into an explicit analytical contribution.
- *Analytical framework*: an assumption-axis matrix (rows = assumptions in SQ3; columns = camps), with each cell marked as evidence-for / evidence-against / untested. Section 6 (Open Challenges) is built from the "untested" cells.
- *Validity safeguards*: (a) every quoted number is checked against the PDF (Phase 2 queue below); (b) counter-evidence is reported (see §4.2 and §4.3 corrections); (c) search limitations are stated in the paper's method section.

** 4.2 Disconfirmation test: "no PIM paper attempts a dynamic-graph design"
*Result: the claim survives only in narrowed form.* Targeted searches found no dynamic/streaming-graph PIM design at ISCA/MICRO/HPCA/ASPLOS in 2021–2026, but dynamic-graph PIM work does exist outside those venues:
- Kim et al., "Things to Consider to Enable Dynamic Graphs in Processing-in-Memory", MEMSYS 2020: a position/analysis paper ([[https://www.memsys.io/wp-content/uploads/2020/10/p315-kim.pdf][PDF]]).
- "Accelerating dynamic graph computation via space-aware mapping approach in computing-in-memory systems", /J. Supercomputing/ 2026: a fully-dynamic-graph PIM mapping ([[https://link.springer.com/article/10.1007/s11227-026-08883-x][Springer]]). Venue confirmed; authors and numbers still to be checked.
- Moctopus (arXiv 2024): PIM graph *database* with batch updates. Unreviewed, so mention it only as a preprint, if at all.

- *Full-text update (see extraction-sheet.org)*: the GrAPL 2025 UPMEM triangle-counting paper (#23) evaluates *insert-only batched updates with a full recount*. PIM beats the CPU there only because COO avoids CSR rebuilds, and it loses on static graphs. It is not an incremental dynamic-graph PIM design.

*Rewrite the claim as*: "Within the top architecture venues surveyed, no PIM design targets streaming or evolving graphs; the problem has been raised (MEMSYS 2020) and addressed only in journal and preprint work [refs]." This is more defensible, and the honest caveat strengthens the Open Challenges section.

** 4.3 Critical-systems search (DSN + targeted)
*Result: the original gap claim is partly overstated and must be corrected.*
- *Security*: no longer "exactly one" paper. MGX (ISCA 2022) evaluates memory protection on a graph accelerator, and IMPACT (DSN 2025) shows PIM introduces new timing channels. Corrected framing: /security has been studied only for each camp separately (memory protection for DSAs, timing channels for PIM); no work compares the two camps' attack surfaces on graph workloads./
- *Dependability*: still a gap. ReRAM fault-tolerance work exists for DNN/GNN workloads, but none was found for classical graph analytics on ReRAM PIM (GraphR, Spara, GaaS-X), despite stuck-at faults affecting the stored adjacency matrix. GraphR argues PageRank-style iterative algorithms are error-tolerant; that argument does not cover BFS/SSSP reachability results. *This is an argument for the paper, not a citation*: present it as an open challenge, clearly marked as analysis.
- *Predictability*: still a gap. No worst-case-timing work found. Glign (concurrent-query interference) remains the nearest related work.
